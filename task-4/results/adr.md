# ADR: выбор Spring Batch как технологического решения для ETL-операций TradeWare

* Статус: принято (accepted)
* Дата: 2026-09-25
* Контекст: задание 4 спринта 5 (кейс TradeWare)

## 1. Контекст и проблема

TradeWare развивает складские решения для малого и среднего бизнеса: API для
интеграции со складскими системами и управления остатками. Текущая
инфраструктура - это монолит на Java 11 / WildFly, БД PostgreSQL, перенесённая
в GCP, и файловое хранилище GCS. Загрузка и обработка отчётов об остатках
выполняется в онлайн-режиме.

Симптомы в пиковые периоды (весна-лето, крупные поставки):

* отчёты по остаткам "висят", обновления позиций приходят с задержкой или не
  применяются;
* замедляется ERP-интерфейс при формировании складских заданий и приёме
  материалов;
* API для логистических партнёров и региональных складов страдают от задержек и
  взаимного блокирования;
* при ошибках трудно свести логи и метрики в единую картину.

Причины (из анализа кейса):

1. Построчная обработка записей прямо в транзакционной БД перегружает её
   ресурсы и конкурирует с онлайн-трафиком.
2. Отчётность, которую можно вынести в ночное окно, считается в реальном
   времени.
3. Нет пакетного конвейера: нет чтения порциями (chunk), нет повторных попыток
   (retry), нет обработки ошибочных записей (skip), нет идемпотентного
   перезапуска.
4. Нет централизованного сбора логов и метрик пакетных операций (только логи в
   файл и мониторинг VM/WildFly).

Ограничения и требования:

* максимальная зафиксированная нагрузка - около 400 000 строк в сутки, в пиковые
  дни в 2-3 раза больше;
* целевое время обработки отчёта на 2 000 строк - до 30 секунд;
* ожидается 100-150 параллельных загрузок в пиковые часы;
* нужны гибкое проектирование пайплайна, ветвление и retry;
* решение должно интегрироваться с Java-экосистемой и позволять постепенно
  выносить функциональность из монолита в сервисы (миграция в микросервисы).

## 2. Рассмотренные варианты

| Критерий | Spring Batch | Apache Airflow | k8s Job | Apache Spark |
|---|---|---|---|---|
| Конфигурация cron-расписания | Из коробки нет, ставится внешним планировщиком (k8s CronJob / Cloud Scheduler / Quartz) | Есть (собственный scheduler, cron-выражения) | Нет, cron задаётся на уровне k8s CronJob | Нет, нужен внешний планировщик |
| Сложность реализации логики обработки данных | Низкая для Java-команд: chunk-ориентированная модель, готовые reader/processor/writer | Средняя: логика на Python (operator/task), для Java-логики нужен отдельный сервис | Высокая: всю логику пишем вручную, включая транзакции и перезапуск | Средняя-высокая: другой стек (Scala/PySpark), свой кластер и оптимизация |
| Ресурсоёмкость | Низкая: обычное Java-приложение, ресурсы только на время выполнения задания | Высокая: scheduler + webserver + metadata DB + workers | Низкая: минимальный рантайм | Очень высокая: драйвер + исполнители, память на shuffle |
| Масштабируемость и сложность масштабирования | Средняя: партиционирование шагов, remote chunking, но нужна настройка | Высокая: горизонтальное масштабирование воркеров | Средняя: масштабируется количество Job/Pod, но логика масштабирования - на нас | Очень высокая: линейное распределение вычислений |
| Развёртывание в облаке и интеграция с микросервисами | Простая: контейнер (Cloud Run Jobs / GKE Job), нативная интеграция с Java/Spring | Средняя: отдельный сервис-оркестратор, интеграция с Java через API/операторы | Простая: стандартный Pod/Job в k8s | Средняя: отдельный кластер, интеграция с Java через файлы/коннекторы |
| Логирование и мониторинг | Micrometer + Actuator + SLF4J, метрики шагов, интеграция с Prometheus/ELK | Собственный веб-UI, логи/Audit Log, но свой стек | Логи Pod + внешние системы | Spark UI + внешние системы, метрики свои |
| Соответствие стеку TradeWare (Java 11, WildFly) | Полное | Частичное (Python-сервис рядом с Java) | Полное (любой язык) | Частичное (новый стек) |

Вывод из сравнения: для объёма 400 000 строк в сутки (с пиками до ~1-1.2 млн)
и команды с Java-опытом Spark избыточен, Airflow добавляет отдельный
инфраструктурный сервис ради оркестрации одного пайплайна, а k8s Job даёт
минимум готовых механизмов. Spring Batch закрывает именно ETL-логику: чтение
порциями, обработку, запись пачками, транзакции, retry/skip и перезапуск.

## 3. Решение

Использовать Spring Batch как движок ETL-операций, оформив его отдельным
контейнеризованным приложением (Spring Boot + Spring Batch) рядом с монолитом.

Ключевые элементы решения:

* Job-launcher и пакетный модуль - отдельный сервис (JVM), который запускается
  по расписанию (k8s CronJob или Cloud Scheduler + Cloud Run Jobs в GCP), а не
  встроен в онлайн-монолит.
* Chunk-ориентированный шаг: `ItemReader` (CSV из GCS) -> `ItemProcessor`
  (валидация и обогащение из справочной БД) -> `ItemWriter` (пакетная запись в
  БД номенклатуры).
* Retry и skip на уровне шага: временные сбои БД/хранилища повторяются, а
  ошибочные строки пропускаются, а не роняют весь запуск.
* Идемпотентность: запись через upsert по ключу товара, повторный запуск
  безопасно перезаписывает данные.
* Наблюдаемость: Micrometer (метрики шагов, длительность, число прочитанных,
  записанных и пропущенных записей) и структурированные логи SLF4J с отправкой
  в ELK (реализуется в задании 5).
* Постепенный вынос: монолит вызывает batch-модуль по API и/или по событию, при
  этом онлайн и пакетная обработка разведены по разным нагрузкам.

### Поток ETL

`product-data.csv` (CSV в GCS/файловая система) -> чтение порциями ->
обогащение данными о лояльности из таблицы `loyality_data` по `productSku` ->
запись в таблицу `products` (upsert по `productId`) -> метрики и логи ->
уведомление онлайн-монолита о завершении.

## 4. Последствия

### Положительные

* Онлайн-трафик и пакетная обработка разведены: загрузка больше не блокирует
  ERP и API партнёров.
* Появляются retry, skip и перезапуск задания, которых не было в онлайн-коде.
* Нагрузка обрабатывается пачками (chunk), число обращений к БД резко падает.
* Решение нативно для Java-команды и совместимо с последующим переходом на
  микросервисы.
* Готовые метрики и логи упрощают диагностику (задание 5).

### Отрицательные и ограничения

* Spring Batch не даёт cron-расписания из коробки - нужен внешний планировщик
  (k8s CronJob / Cloud Scheduler). Это осознанный выбор: оркестрацию берёт на
  себя инфраструктура.
* Для облачного развёртывания нужен образ и способ запуска Job (Cloud Run Jobs
  или GKE Job).
* Партиционирование и масштабирование шага требуют отдельной настройки
  (`Partitioner`, `TaskExecutor`).
* Возможны сетевые задержки при чтении больших CSV из GCS - нивелируются
  потоковым чтением и размером чанка.

## 5. Верхнеуровневый план внедрения

1. Вынести обработку отчётов в отдельный Spring Boot + Spring Batch сервис.
2. Настроить планировщик: k8s CronJob (локально/в k8s) или Cloud Scheduler +
   Cloud Run Jobs (GCP) с ночным окном.
3. Реализовать шаг ETL: чтение CSV, валидация, обогащение из справочной БД,
   пакетная запись в `products` (upsert).
4. Включить retry/skip и идемпотентные записи.
5. Подключить метрики (Micrometer/Prometheus) и логи (SLF4J -> filebeat -> ELK).
6. Построить дашборды и алерты (задание 5), затем добавить API-запуск и трейсинг
   (задание 6).
7. По мере роста объёмов включить партиционирование по клиенту/складу.

## 6. POC

В рамках задания реализован и локально запущен POC:

* Spring Batch-приложение читает `product-data.csv`;
* обогащает строки данными о лояльности из таблицы `loyality_data`;
* записывает результат в таблицу `products`;
* запускается через `docker compose` вместе с PostgreSQL.

Код и инструкции - в каталоге `results/batch-processing`, результаты запуска -
в `results/screenshots`.
